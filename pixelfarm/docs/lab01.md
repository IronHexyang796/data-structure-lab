## 2. 关键实现说明

### 2.1 扩容（barn_grow）

三件事：

- **什么条件扩容**：`b->count >= b->cap`，也就是「已经装满了才扩」。这里我一开始写反成 `count < cap`，后果见第 5 节。
- **扩到多大**：`newcap = b->cap * 2`，翻倍而不是 `+8`。翻倍的话，装 n 个东西总共只扩容约 log₂n 次，均摊到每次入库是 O(1)；如果每次只加 8，装 n 个要扩 n/8 次，每次都把全部数据搬一遍，总代价就变成 O(n²)。
- **realloc 失败怎么办**：结果先接到临时指针 `p`，判空之后再赋给 `b->data`。如果直接写 `b->data = realloc(...)`，一旦返回 NULL，`b->data` 就被覆盖成 NULL，原来那块内存的地址丢了 —— 既读不到数据，也 free 不掉，是内存泄漏。用临时指针接住，失败时 `b->data` 还是原来的，数据完好，只是这次扩容没成功。
> 扩容必须先用临时指针接住 realloc 的结果。
```c
int barn_grow(Barn *b)
{
    if (!b) return PF_PARAM;
    int newcap = b->cap * 2;                                  /* 翻倍 */
    Item *p = (Item *)realloc(b->data, sizeof(Item) * newcap); /* 先接临时指针 */
    if (p == NULL) return PF_NOMEM;   /* 失败：原数据还在，b->data 不能动 */
    b->data = p;                      /* 成功了才替换 */
    b->cap  = newcap;
    cost_malloc(1);                /* 搬东西需要花时间：记一次内存分配，引擎折算成游戏时间 */
    return PF_OK;
}
```

### 2.2 插入 / 删除的移动方向

这周的仓库只有**尾部追加**（`barn_add` 把新作物写在 `data[count]`，然后 `count++`），没有按下标插入，所以真正会挪数据的是**删除**。

删除时是**从前往后补**：删掉 `pos` 之后，`pos+1` 搬到 `pos`、`pos+2` 搬到 `pos+1`…… 必须从前往后，因为每个元素都搬到它前面一格，先搬前面的不会覆盖还没搬的数据。如果反过来从后往前搬，`data[pos+1]` 会先被 `data[pos+2]` 覆盖，等轮到 `data[pos]` 时拿到的是被改过的值，整段数据就串位了。

对应的，如果以后要实现**按下标插入**，方向必须**从后往前**挪：从 `data[count]` 开始依次把 `data[i]` 写到 `data[i+1]`，给新元素腾出 `pos` 这个空位。从前往后挪会把后面的数据整段覆盖掉。
**插入是"从后往前"（给新元素腾位置），删除是"从前往后"（把洞填上）**
```c
int barn_remove_at(Barn *b, int pos, Item *out)
{
    if (!b || !out) return PF_PARAM;
    if (b->count == 0) return PF_EMPTY;
    if (pos < 0 || pos >= b->count) return PF_PARAM;
    *out = b->data[pos];                        /* 1. 先把要删的备份出去 */
    for (int i = pos; i < b->count - 1; i++) {  /* 2. 后面的一次往前补一格 */
        b->data[i] = b->data[i + 1];
        cost_move(1);                           /* 每挪一次记一次代价 */
    }
    b->count--;
    return PF_OK;
}
```

## 4. 性能观察

这周的仓库**没有*按下标插入***，`barn_add` 只做尾部追加，同种作物直接合并数量。
模板里「头插 / 随机位置插」这两行在这周不成立，真正把代价推上去的是 `barn_remove_at`。
下面是我用一个临时 C 程序直接读 `cost_move` 计数器量出来的数（不是估的）：

| 场景 | 移动次数 | 说明 |
|---|---|---|
| 尾插 8 种不同作物 | 0 | 直接写 `data[count]` 再 `count++`，谁都不用挪 |
| 装满后再插第 9 种（触发扩容） | 0（`malloc` 1 次） | `realloc` 由系统搬内存，`cap` 从 8 变 16，`b->count` 不变 |
| 1000 条删下标 0（最坏情况） | 999 | 除第 0 个以外全部前移一个单位 |
| 删最后一个（最好情况） | 0 | 循环 `i < count-1` 一次都不进，直接把最后一个踢掉，前面的都不用动 |
| 删中间（n≈998） | 498 | 平均挪一半，大约五百次，正好 `(n-1)/2` |
| 1000 次都删下标 0 | 496506 | 第一次删除挪动999下，第二次998下...一直到第1000次挪动一下，正好是一个差值d=1的等差数列=（ 999 + 998 + ... +1） = 999 * 1000 /2 ≈ 50 万次 ≈ n²/2，这就是 `O(n²)` 的来源 |

结论：**尾插是 O(1)，删除是 O(n)，如果连续在最前面删元素，时间复杂度会从 O(n)恶化成 O(n²)**。
订单交付和 `V` 出货走的都是 `barn_remove_at`，一天几十次，30 天累积下来一万五千次移动、38 分钟游戏时间 —— 和任务书里 `stub.c` 那份最笨实现的 16494 次比较 / 15428 次移动 / 39.5 分钟基本持平。
这也说明：**我的实现虽然对了，但没有比最笨的实现聪明**，因为算法一样。
**如果要降下来**，得改成「删除时不移动、留空洞复用」或者换成链表结构，这是后面实验的需要做的事。

## 5. 踩过的坑

**坑 1：环境与工具的问题**

- `Windows` 下的 ` make test01 `报错` No rule to make target `
- 原因：老师提供的` Makefile `里用了` sed、ls、/dev/null `等 `Linux` 命令，`Windows` 自带的 `PowerShell` 不认。
- 怎么发现的：代码明明写了目标，`make` 却死活说找不到。
- 怎么解决：装 `Git Bash`，或者绕过 `Makefile` 直接编译` build/t01_field.bin `,或者切换默认终端，但是老师新给的压缩工程包解决了这个问题，可以直接使用 `` Ctrl + ` ``唤醒`PowerShell`终端输入命令。

**坑 2：扩容条件写反了，仓库容量指数膨胀**

- 我一开始以为是：`if (count < cap) grow()` 就是*还有空位，可以往里放*，读起来挺顺。
- 实际原因是：条件写反了。`count < cap` 表示*没满*，这时候去扩容是白扩；而真正装满（`count == cap`）的时候反而跳过了扩容，直接往 `data[cap]` 写 —— 越界。更糟的是每次入库都扩一次，容量一路翻倍，**仅加 8 种作物，`cap` 就从 8 变成了 2048**。
- 怎么发现的：`pf test 1` 是绿的（它只检查 `cap >= 12`，膨胀也能过），所以我写了个临时 C 程序，直接调 `barn_add` 然后打印 `count` / `cap`，一眼就看见 `count=8 cap=2048`；再数 `malloc` 计数器，发现扩容被调了 8 次而不是 1 次。
- 怎么改的：把条件改成 `count >= cap`。改完再跑同一个程序：加 8 种作物 `count=8 cap=8`，加第 9 种才 `cap=16`、`malloc=1`。`pf test 1` 仍然 31 项全绿。

> 顺带还改掉一处：扩容最后一行原来写的是 `advance_time(newcap)`，等于每次扩容硬推 `newcap` 秒游戏时间（2048 秒 ≈ 34 分钟），而且这部分**不计入计算已耗**，时间悄悄溜走。任务书要求的是 `cost_malloc(1)`，改成它之后引擎自己折算，账面才对得上。

**坑 3：把结构体字段当成函数调了（把变量函数用了）**

- 现象：`src/field.c` 编译不过，报 `implicit declaration of function 'seed_cost'`。
- 我一开始以为是：`seed_cost` 是个函数，我没 include 对应的头文件。
- 实际原因是：`seed_cost` 是 `Crop` 结构体里的一个字段，`crops[i].seed_cost` 才对，写成 `seed_cost(crop_id)` 就成了调用一个不存在的函数。
- 怎么发现的：编译器报错最后一行指到 `crop->seed_cost` 的用法，回去翻 `include/farm.h` 第 71 行，确认它确实是个 `int` 字段。
- 怎么改的：`if (g_farm.gold < crop->seed_cost) return PF_EMPTY;`，同理 `g_farm.gold -= crop->seed_cost;`。

## 7. 拔高任务（⭐⭐⭐ 搬运成本对比，25 分）

三档里选了 ⭐⭐⭐。⭐ 那档要装 MySQL、导 10 万条、掐表对比 EXPLAIN；⭐⭐ 那档要录 20 秒屏幕。这一档只要一个 C 程序加一张表，数字全部可复现，跑一条命令就有。

### 7.1 怎么测的

程序在 `tools/bench_barn.c`，跑 `pf bench-barn` 一条命令。

第 1 周的仓库接口只有尾部追加（`barn_add`），没有「按下标插入」，所以 bench 里补了一个 `insert_at`：从尾部往 `pos` 逐个后移一格，每挪一件调一次 `cost_move(1)`。**没有改老师给的任何接口**，这个函数只活在 bench 里。

三组实验的起点都一样：`barn_init(&b, 8)`（跟游戏开局容量一致），每种方式各插 1000 件。随机那组用固定种子，别人跑出来数字一样，可以复核。

### 7.2 实测结果

| 场景 | 移动次数 | malloc | 折算时间（仅移动） | 理论值 | 偏差 |
|---|---|---|---|---|---|
| ① 尾部插入 1000 次 | **0** | 7 | 0.0 秒 | 0 | — |
| ② 头部插入 1000 次 | **499500** | 7 | 49950 秒 ≈ **13.9 小时** | 499500 | 0.0% |
| ③ 随机位置插入 1000 次 | **256178** | 7 | 25618 秒 ≈ **7.1 小时** | 249750 | +2.6% |

`out/bench_barn.csv` 里存着同样一份数据。

### 7.3 三个数字怎么读

- **尾部是 0**：数据本来就在末尾，`data[count] = x; count++`，一件都不用挪。这就是为什么一天往仓库里塞几十次货，从来不会卡。
- **头部 499500 次 ≈ 13.9 小时游戏时间**：第 1 次插挪 0 件，第 2 次挪 1 件……第 1000 次挪 999 件，`0+1+…+999 = 999×1000/2`。一个游戏日只有 86400 秒，光这一项就吃掉 **0.6 个游戏日**，比睡一觉还久。
- **随机 256178 次，比理论高 2.6%**：理论按「平均挪一半」估的是 `n²/4 ≈ 249750`。实测偏高是随机位置的波动，插得靠前的次数多了一点；量级完全对得上，说明模型没错。
- **malloc 只有 7 次**：容量 8→16→32→64→128→256→512→1024，塞 1000 件只扩容 7 次。翻倍扩容的均摊是 O(1)，所以「收 1000 筐」不会因为扩容而卡。

### 7.4 一句结论

**仓库这种只往尾巴上加、偶尔整条拿走的用法，数组最合适；一旦要频繁从头部或中间插，就该换链表。**

账很直白：同样 1000 次操作，追加是 **0** 次移动，头插是 **49.95 万**次移动、折合 **13.9 小时**游戏时间。链表插进去只改两个指针，一件数据都不用搬；代价是想找第 500 件得从头数过去
> ：**「常用的放前面」只对查找有用**（顺序查找时前面几次就命中），对移动成本没有任何帮助，反而让后面每次插入都更贵。

### 7.5 一个额外发现

引擎只统计显式调用 `cost_move()` 的搬动。`realloc` 扩容时内部那次整块拷贝**没有计入**移动次数，所以表里的数字略低于真实代价。另外每次 `malloc` 单独折算 2 秒（7 次共 14 秒），这一笔我也没混进「折算时间」列 —— 两笔账分开放，才对得上。
