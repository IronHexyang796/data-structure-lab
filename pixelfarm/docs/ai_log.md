## 第 1 周 · lab01

### A1 让 AI 造数据
- 我给的提示词：按任务书 §10 生成一张作物表，40 种，字段 `name,grow_days,seed_price,sell_price,season,water_need`；要有 *3 种高风险高回报*的作物；价格和生长天数要合理。
- 它给了什么：40 行 CSV，表头就是我要的那六列，数字看着也像样。
- 我怎么验证的：直接丢进 `data/crops.csv` 跑 `pf demo`；再用 `pf json` 导出 `web/data.json`，数里面到底进去了几种作物；另写了个小脚本按「卖价 ÷ 种子价」「日收益」「季节 × 需水量」三个角度筛异常。
- 发现的问题：
  - **最要命的是表头本身就读不进去。** `pf demo` 打出「作物表读不到，用一份内置的应急数据先顶着」。翻 `engine/loop.c` 才看见解析器是 `sscanf(line, "%d,%19[^,],%d,%d,%d,%d")` —— 要 6 列，而且**第一列必须是数字 `id`**。AI 给的表以 `name` 开头，拿 `小麦,4,10,25,春,2` 去套，第一个字段就不是数字，一行都匹配不上，等于 0 种作物。
  - 价格单位也不对：引擎里金币的内部单位是「分」，开局 500 元 = 50000，AI 给的小麦种子写 `10`，等于 0.1 元。
  - 数字上真不合理的有 4 条：人参 4.2 倍、灵芝 4.4 倍、冬虫夏草 4.3 倍、霸王花 4.4 倍（卖价 ÷ 种子价，任务书写的上限是 4 倍）；其中灵芝、冬虫夏草还是冬季作物，`water_need` 却给到 5。
- 我改了什么：
  - 原表备份成 `data/crops_任务书格式_备份.csv`（`season` / `water_need` 两列保留着，挑数据要靠它）。
  - 重写成 `id,name,grow_days,seed_cost,price,demand,season,water_need`：补 `id` 1~40；价格 ×100 转成分；`demand` 按越便宜需求越大用 `1200 ÷ 卖价` 反推，夹在 20~120。引擎只取前 6 个字段，后面两列不影响解析。
  - 改完 `pf demo` 不再报警告，`web/data.json` 里 `crops` 正好 **40** 条。
  - 结论：**AI 给的数据「看起来对」和「能跑」是两件事**。光抽查数值不够，得先让它过一遍真正的读取路径。

### A2 让 AI 找 bug
- 我贴了什么代码：`src/field.c` 第四部分整个仓库模块，8 个函数约 200 行（`barn_init` / `barn_destroy` / `barn_grow` / `barn_add` / `barn_remove_at` / `barn_find` / `barn_load_csv` / `barn_save_csv`）。
- 我怎么验证的：写了个一次性的 `_probe_ai.c`（验完就删了），把 `cost_compare` / `cost_move` / `cost_malloc` / `advance_time` / `pf_rand` / `crop_by_id` 全桩成空函数，只链接 `src/field.c`，这样能撇开引擎单独调某个函数，直接打印 `count` / `cap`，再用 `_msize()` 量实际分配到手多少字节。每种说法对应一个小场景，一共跑了六个。
- 它说的问题（逐条判断）：

  1. **「没有处理空仓库」** → 我验证：**错**。
     逐个入口试过：`barn_remove_at(空, pos=0)` 返回 `-2`（`PF_EMPTY`）、`barn_find(空)` 返回 `-1`、`barn_save_csv(空)` 只写一行表头并返回 `PF_OK`、往空仓库 `barn_add` 正常写进 `data[0]`。四个入口都有明确返回，它连「哪个函数没处理」都指不出来。

  2. **「对未初始化的 Barn 会产生越界崩溃（野指针）」** → 我验证：**对，而且比它说的更糟**。
     它说会「崩溃」，实际是**静默越界**：`Barn b = {0, 0, NULL}` 直接 `barn_add(&b, 7, 3)`，返回值居然是 `PF_OK`（成功），`count` 变成 1，但 `cap` 还是 **0**。`_msize(b.data)` 量出来实际只给了 **1 字节**，而一个 `Item` 是 **12 字节** —— 写进去的 12 字节全是越界的，编译器不报，测试也不红。
     根因在 `barn_grow`：`newcap = b->cap * 2`，`cap=0` 时算出 0，`realloc(p, 0)` 返回一个 1 字节的块**而且不是 NULL**，于是 `p == NULL` 那个判断根本没触发，函数一路返回「成功」。栈上垃圾值更直接：`cap = -1431655766`，拿这个去 `realloc` 必崩。
     **改法**：`barn_grow` 和 `barn_add` 开头各加一句 `if (b->cap <= 0) return PF_PARAM;`。改完实测：全 0 的 Barn 返回 `-1`、栈上垃圾 Barn 返回 `-1`，一次都没碰那个指针，`cap` 也没被改写。

  3. **「如果 out 指针传入了一个非法地址」** → 我验证：**一半错，一半做不到**。
     `out = NULL` 这半边是**错**的：代码里 `if (!b || !out) return PF_PARAM;` 早就判了，实测传 NULL 返回 `-1`，仓库的 `count` 也没被改坏。它没看代码就开口。
     非 NULL 的非法地址（我传 `(Item*)0x8`）确实崩，进程退出码 **139**（SIGSEGV）。但这条**没法修**：C 语言没有任何办法判断一个非 NULL 指针指向的内存能不能写，只有真正写下去的那一刻由内核发现。要我「加个检查」就是在写假代码。

  4. **「内存泄漏」** → 我验证：**没找到**。
     跑 2000 轮 `barn_init → 连续 add 10 次（每轮都触发扩容）→ barn_destroy`，进程占用从 **8780 KB 涨到 8788 KB**，两轮只差 8 KB，是运行时噪声，不是每轮泄漏 24 字节那种线性增长。又逐条查了提前 `return` 的路径：`barn_load_csv` 的每个失败分支都配了 `fclose`；`barn_grow` 里 `realloc` 失败时保留了原指针，没有先 free 再赋 NULL（那才是真丢内存）。
     真会漏的是**调用方**：只 `barn_init` 不 `barn_destroy`。那是用法问题，不是这几个函数的错。

  5. **「数据残余」** → 我验证：**对，但它没说到点子上**。
     这话太含糊，我拆成两种情况分开测：
     - 「删除后 `data[count]` 还留着旧元素」—— **有，但无害**。逻辑数据只看 `[0, count)`，`barn_save_csv` 也只写 `count` 条，读不出去。这只是逻辑删除的正常现象。
     - 「新入库的元素没初始化」—— **这是真的，而且会污染存档**。`barn_add` 只写了 `crop_id` 和 `count`，**`quality` 从头到尾没人赋值**。我先把一块内存填成 `0xAB` 再 free，让 `barn_init` 复用这块内存，然后 `barn_add`：第一件读到 `quality = 6422864`，第二件更直接，`-1414812757`（就是 `0xABABABAB`）。`barn_save_csv` 会把这个垃圾值原样写进 CSV。
     **改法**：`barn_add` 里补一行 `b->data[b->count].quality = 1;`（1~5 星，未评级给 1 星；依据是任务书进阶部分 MySQL 建表写的 `quality TINYINT DEFAULT 1`）。改完存档里是 `3,5,1`。

- **我否决了哪条，为什么**：
  **第 3 条（out 非法地址）和第 1 条。**
  第 3 条不是「代码有 bug」，是「C 语言做不到」。它给的是一条**在 C 里无法实现的建议**，照着写只会得到一段永远为真的假检查，反而让人以为安全了。而且它前半句「out 可能为 NULL」我代码里明明判了 —— 典型的没读代码就开口，这跟任务书里提醒的那个坑一模一样。
  第 1 条是**纯猜**：四个入口我全测了，空仓库的返回值各不相同但都正确，它连指向哪个函数都说不清。
  五条里 **2 条真、2 条误报、1 条不可实现**，命中率 40%。但它第 2 条确实指到了我自己没测过的地方 —— 我只测过「装满能扩容」，从来没想过「没初始化会怎样」。**所以 AI 的话不能整段信，也不能整段丢，得拆开一条条跑。**

### A3 让 AI 当陪练
- 它问的 5 个问题：**1.** 扩容的时候，底层内存到底发生了什么？你原来的那些元素是怎么到新内存里去的？ **2.** “单次操作偶尔很贵、但平均下来很便宜”的分析，叫什么？ **3.** 你的删除操作，删掉一个元素之后，数组里发生了什么？如果我不停地删，数组元素越来越少，你会不会缩容？如果会，怎么缩？如果不会，为什么？ **4.** 你的查找操作，是顺序查找还是二分查找？为什么？ **5.** 扩容的复制量从“每个大结构体”变成“每个指针”，代价小了多少？ 数量级上怎么描述？用指针存元素，会带来什么额外代价或麻烦？
- 我答不上来的：**第 3 题的缩容时机**（其余四题当场答上来了）。被追问「删到剩一半就缩」在临界点会怎样时卡住。它后面解释的是：**2.** 把一串操作连起来算总代价，再摊到每次操作上。所以它叫——`摊还分析`（`amortized analysis`），这里具体是“`摊还 O(1)`”  **3.** 问题：如果“元素数降到容量的一半就缩容”，那么在临界点附近反复删一个、插一个，每次都会触发一次缩容或扩容，每次都是 `O(n)` 的搬移。摊还代价就退化回 `O(n)`，之前的 `O(1)` 全白费了。正确做法：缩容阈值要留“缓冲”，不能和扩容阈值贴在一起。通常设成元素数降到容量的 1/4 时才缩成一半。这样缩容后容量是元素数的 2 倍，中间留出了足够空位，必须连续删很多或插很多才会再次触发搬运，摊还代价才能保持 `O(1)`。核心记住一句话：扩容和缩容的触发点之间必须有间隔，否则会在临界点来回抖动。 **4.** 二分查找要求数据有序。 但你的动态数组插入/删除时只做“挪位”，并不维护顺序。要支持二分，就得在插入时找到正确位置再插入——这一找一插，代价是 `O(n)`（找 `O(log n) `或` O(n) `，但挪位本身就是` O(n) `）。也就是说，每次插入/删除都变贵了。所以真正的取舍是：顺序查找用 `O(n)` 的查找代价，换来了插入/删除的简单和 `O(n)` 挪位；二分查找把查找降到 `O(log n)`，代价是插入/删除时必须额外维护有序，操作更重。 一句话：用“维护有序的插入代价”换“更快的查找”。 不是简便 vs 复杂。
- 后来我怎么搞明白的：在devC++中模拟了对应情况的动态数组增删改查。
- 我的收获：更清楚地明白了数组的底层逻辑和代价实现，以及存储删除插入的算法优化方向。
